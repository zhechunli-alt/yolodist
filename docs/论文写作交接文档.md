这份文档的目标不是记录开发流水，而是让新的撰写者在**不重新翻代码、不重新核对日志**的前提下，直接掌握本项目论文所需的核心事实、实验结论、图表资产、演示系统实现、数据库结构以及当前最安全的写法。

## 1. 项目一句话定位

本项目研究的是：在 PCB 缺陷检测任务上，围绕 `YOLO11` 轻量学生模型，设计并验证融合**边缘先验**与**特征增强**机制的 `EPFA-Lite` 模块，并进一步考察知识蒸馏在不同 PCB 数据集上的增益稳定性，同时补充一组非 YOLO 经典检测器作为对比基线。

## 4. 模型体系、命名与参数量

### 4.1 主线模型命名

项目内部主线模型可以分成三类：

- `baseline`：标准 `YOLO11n`
- `student_plain`：轻量学生基线
- `student_epfa`：加入 `EPFA-Lite` 的学生模型
- `distill_plain / distill_epfa`：基于 teacher 蒸馏得到的学生模型

### 4.2 参数量

主线模型参数量如下：

| 模型 | Params |
| --- | ---: |
| `baseline` | `2,624,080` |
| `student_plain` | `1,286,179` |
| `student_epfa` | `1,286,221` |
| `distill_plain` | 与对应 student 结构相同 |
| `distill_epfa` | 与 `student_epfa` 相同 |

关键结论：

- `EPFA-Lite` 相比 `student_plain` 仅增加 `42` 个参数。
- 也就是说，`EPFA-Lite` 的改进成本极小，但在部分数据集上能带来可观提升。

### 4.3 fair 与 tuned 的含义

#### `fair`

`fair` 表示当前论文建议采用的公平蒸馏版本，满足：

- teacher 使用完整训练后的基线最优权重
- student 与 distill 统一使用 `100 epoch`
- 使用独立伪标签数据集，不回指原始标签目录
- 蒸馏核心配置：
  - `distill_alpha = 0.5`
  - `enable_feature_kd_loss = true`
  - `feature_kd_alpha = 0.1`

#### `tuned`

`tuned` 表示后续尝试提升 `Recall + mAP50-95` 的蒸馏超参数版，但最终没有形成稳定优于 `fair` 的结论，因此不建议写入主结果表。

### 5.2 安全结论

可以放心写入正文的结论：

1. `baseline` 仍然是三个数据集上的最强上界。
2. `student_epfa` 在 `DeepPCB` 与 `PKU-Market-PCB` 上优于 `student_plain`，说明 `EPFA-Lite` 对轻量学生模型有效。
3. `EPFA-Lite` 参数开销极小，相对 `student_plain` 仅增加 `42` 个参数。
4. 蒸馏收益存在数据集依赖性，当前公平蒸馏仅在 `PKU-Market-PCB` 上相对 `student_epfa` 显示出一定提升。

不建议写死的结论：

- “蒸馏在全部 PCB 数据集上都有效”
- “EPFA-Lite 在所有数据集上都提升”
- “tuned 蒸馏优于 fair 蒸馏”

## 7. 蒸馏策略探索：fair vs tuned

来源：

- [runs/paper_tables/pcb_ablation.csv](/root/workspace/yolodist/runs/paper_tables/pcb_ablation.csv)

| 数据集 | student_epfa mAP50-95 | fair mAP50-95 | tuned mAP50-95 | 结论 |
| --- | ---: | ---: | ---: | --- |
| DeepPCB | 0.6984 | 0.6865 | 0.6639 | `tuned` 不如 `fair` |
| PKU-Market-PCB | 0.3533 | 0.3798 | 0.3652 | `fair` 最优 |
| DsPCBSD+ | 0.5343 | 0.5231 | 0.5167 | `fair` 稍优于 `tuned` |

推荐写法：

> 为提升前景区域约束与定位蒸馏效果，本文进一步设计了 tuned 蒸馏版本。然而实验结果表明，该版本未能在三个 PCB 数据集上形成稳定优于 fair 的一致收益，因此最终正文采用 fair 蒸馏结果作为正式报告。

## 9. DeepPCB 推理时延统计

为了避免直接使用前端页面体感耗时，本项目额外做了一次统计口径更干净的 DeepPCB 推理时延基准测试。

来源：

- [runs/paper_tables/deeppcb_inference_latency_benchmark.csv](/root/workspace/yolodist/runs/paper_tables/deeppcb_inference_latency_benchmark.csv)
- [runs/paper_tables/deeppcb_inference_latency_benchmark.md](/root/workspace/yolodist/runs/paper_tables/deeppcb_inference_latency_benchmark.md)
- [runs/paper_tables/deeppcb_inference_latency_benchmark.json](/root/workspace/yolodist/runs/paper_tables/deeppcb_inference_latency_benchmark.json)
- [tools/benchmark_deeppcb_latency.py](/root/workspace/yolodist/tools/benchmark_deeppcb_latency.py)

### 9.1 统计设置

- 数据集：`DeepPCB test`
- 样本数：`500` 张
- 预热：每个模型 `5` 张
- 计时口径：`InferEngine.infer()` 返回的 `latency_ms`
- 不包含：
  - HTTP 上传
  - 页面渲染
  - 前端交互等待

### 9.2 结果

| 模型 | Mean(ms) | Median(ms) | P95(ms) | FPS |
| --- | ---: | ---: | ---: | ---: |
| DeepPCB / Baseline-YOLO11n | 9.410 | 9.343 | 9.857 | 106.27 |
| DeepPCB / Distill-EPFA | 8.095 | 8.020 | 8.643 | 123.53 |
| FasterRCNN-R50-FPN | 16.702 | 16.663 | 17.030 | 59.87 |

### 9.3 论文可用结论

- 主线 YOLO 模型推理已稳定在 `10ms` 左右量级。
- `Distill-EPFA` 的推理速度并未因为蒸馏训练而变慢，因为部署时仍然是学生结构本身。
- `FasterRCNN-R50-FPN` 精度更强，但速度明显慢于主线 YOLO 轻量模型。

## 12. 前端缓存、文件状态与数据库

这部分很容易在论文答辩或系统说明中被问到，因此这里单独写清楚。

### 12.1 前端缓存结构

核心状态位于前端模板中的 `state` 对象，主要包括：

- `state.files`
  - 当前导入的全部图片文件数组
- `state.selectedFile`
  - 当前用户正在查看的图片对象本身，不是索引
- `state.filePage`
  - 图片分页页码
- `state.filePageSize`
  - 当前每页图片数，现为 `5`
- `state.modelFileStatuses`
  - 按模型隔离的图片状态缓存
- `state.modelFileResults`
  - 按模型隔离的结果缓存
- `state.detectProgress`
  - 文件夹检测进度
- `state.lastFolderRunModel`
  - 上一次整文件夹检测的模型 key

### 12.2 图片状态逻辑

状态值：

- `idle`：未检测
- `running`：检测中
- `done`：已检测

关键逻辑：

- 图片状态是**按模型隔离**的，不是全局共享。
- 因此同一张图片在不同模型下可能呈现不同状态。
- 如果未切换模型，再次点击“检测整个文件夹”，只会处理 `idle` 或 `running` 的图片。
- 如果切换了模型，再点击“检测整个文件夹”，会从头到尾重跑全部图片。

### 12.3 为什么之前状态会乱

项目中期曾出现过一个问题：所有模型共用一套 `fileStatuses` / `fileResults`，导致切换模型后“已检测/未检测”状态串扰。这个问题已经修复，当前文档写的是**修复后的真实逻辑**。

### 12.4 后端数据库

数据库类型：

- `SQLite`

数据库文件：

- `/root/workspace/yolodist/service/backend/data/inference_logs.db`

主要表：

- `inference_logs`
  - 每次推理请求日志
- `inspection_records`
  - 每张图的正式检测记录主表
- `detection_items`
  - 每条记录中的检测框明细
- `review_notes`
  - 人工复核批注

### 12.5 什么时候落库

1. 推理请求执行时
   - 写入 `inference_logs`
2. 点击 `检测当前图片` 或 `检测整个文件夹` 并得到结果后
   - 自动写入 `inspection_records`
   - 自动写入 `detection_items`
3. 点击 `保存复核`
   - 写入或更新 `review_notes`

### 12.6 文件持久化位置

上传图片副本目录：

- `service/backend/data/uploads/`

这意味着系统不是只有前端内存缓存，而是：

- 前端有会话级缓存
- 后端有 SQLite 记录库
- 后端有上传图片副本
