# 论文写作交接文档

这份文档面向“接手后直接写论文”的使用场景，目标是让新的撰写者不用重新翻代码和日志，也能直接掌握本项目当前最可信的实验结论、图表素材位置、可安全陈述的创新点，以及不建议误写的内容。

## 1. 项目一句话定位

本项目的论文主线是：在 PCB 缺陷检测任务上，基于 YOLO11 轻量学生模型引入 `EPFA-Lite` 模块，验证其对检测性能的提升，并进一步探索知识蒸馏在不同数据集上的增益稳定性。

## 2. 最终建议采用的数据集与实验主线

建议论文正文以这三套 PCB 数据集为主：

- `DeepPCB`
- `PKU-Market-PCB`
- `DsPCBSD+`

建议主表统一采用以下四组：

1. `baseline`
2. `student_plain`
3. `student_epfa`
4. `distill_epfa_fair`

其中：

- `baseline` 是标准 YOLO11n 上界参考。
- `student_plain` 是轻量学生基础线。
- `student_epfa` 是论文核心改进模型。
- `distill_epfa_fair` 是公平条件下的蒸馏结果，用于说明蒸馏是否真的带来增益。

`distill_epfa_tuned` 只建议作为蒸馏策略探索或附录消融，不建议进入论文主结果表。

## 3. 关键术语

### 3.1 `fair`

`fair` 表示公平条件下的蒸馏版本，主要含义是：

- teacher 使用完整训练后的 `baseline` 最优权重
- 训练轮数与普通 student 统一为 `100 epoch`
- 使用独立的伪标签数据集目录，而不是回指原始数据
- 蒸馏配置固定为：
  - `distill_alpha = 0.5`
  - `enable_feature_kd_loss = true`
  - `feature_kd_alpha = 0.1`

### 3.2 `tuned`

`tuned` 表示在 `fair` 基础上进一步调节蒸馏超参数的实验版本，目的是尝试同时提升 `Recall` 与 `mAP50-95`。但当前结果显示，`tuned` 在三个数据集上都没有稳定优于 `fair`。

- `baseline` 在三个数据集上都是最强上界。
- `student_epfa` 在 `DeepPCB` 与 `PKU-Market-PCB` 上均优于 `student_plain`，说明 `EPFA-Lite` 对轻量学生模型有效。

- `distill_epfa_fair` 在 `DeepPCB` 与 `DsPCBSD+` 上未超过 `student_epfa`，但在 `PKU-Market-PCB` 上相较 `student_epfa` 有一定提升，尤其体现在 `Recall` 和 `mAP50-95`。

建议论文正文写为：

## 6. 当前最安全的论文主结论

以下结论当前可以安全写入论文正文：

1. `EPFA-Lite` 在 `DeepPCB` 和 `PKU-Market-PCB` 上能稳定提升轻量学生模型性能。
2. `EPFA-Lite` 的参数增量极小，相比 `student_plain` 仅增加约 `42` 个参数，几乎不增加模型规模。
3. 蒸馏收益在不同数据集上不稳定，当前公平版蒸馏仅在 `PKU-Market-PCB` 上显示出相对 `student_epfa` 的一定提升。
4. tuned 蒸馏策略未形成一致增益，因此不作为论文主卖点。

以下内容不建议写死：

- “蒸馏在三个 PCB 数据集上都有效”
- “EPFA 在所有 PCB 数据集上都优于 student_plain”
- “tuned 蒸馏优于 fair 蒸馏”

## 7. 推荐论文叙事

### 7.1 方法主线

建议论文核心创新点聚焦为：

- 轻量学生模型
- EPFA-Lite 模块
- PCB 领域导向的边缘先验与轻量通道注意力融合

### 7.2 蒸馏主线

蒸馏不建议作为第一创新点，而应写成：

- 对轻量学生模型的进一步增强探索
- 在不同数据集上的收益不稳定
- 说明工业缺陷检测中的蒸馏策略仍依赖数据特性与 teacher 质量

### 7.3 数据集主次顺序

建议正文叙事顺序：

1. `DeepPCB`
2. `PKU-Market-PCB`
3. `DsPCBSD+`

理由：

- `DeepPCB` 结果最稳，最适合讲清楚方法主线
- `PKU-Market-PCB` 最适合承接蒸馏的“局部有效”结论
- `DsPCBSD+` 更适合作为复杂类别场景下的补充讨论

### 9.2 前端缓存结构

前端核心状态保存在页面 `state` 对象中，最关键的字段包括：

- `state.files`
  - 当前导入的图片 `File` 对象数组
- `state.selectedFile`
  - 当前用户正在查看的图片对象
- `state.modelFileStatuses`
  - `modelKey -> fileKey -> status`
  - 每个模型各自维护自己的图片检测状态
- `state.modelFileResults`
  - `modelKey -> fileKey -> { result, record_uuid, review_note }`
  - 每个模型各自维护自己的检测结果缓存
- `state.fileStatuses`
  - 当前激活模型下的状态视图
- `state.fileResults`
  - 当前激活模型下的结果视图
- `state.detectProgress`
  - 当前文件夹检测进度
- `state.lastFolderRunModel`
  - 上一次文件夹检测所用模型

### 9.3 当前图片状态逻辑

系统对每张图片提供三态标记：

- `未检测`
- `检测中`
- `已检测`

注意：

- 这三态是**按模型隔离**的，不是全局共享。
- 也就是说，同一张图在 `Student-EPFA` 下可能是“已检测”，切换到 `Distill-EPFA` 后仍可能是“未检测”。

### 9.4 文件夹检测逻辑

当前文件夹检测规则如下：

- 若**未切换模型**：
  - `检测整个文件夹` 只处理 `未检测` 或 `检测中` 的图片
  - 已检测图片会跳过
- 若**切换了模型**：
  - `检测整个文件夹` 会从头到尾重新检测全部图片
  - 不再区分旧的图片状态

此外：

- 文件夹检测进行中时，前端禁止切换模型
- 当前已支持 `暂停检测`
- 暂停时不会强杀当前图片，而是在当前图跑完后停止后续任务

### 9.5 数据库位置与表结构

当前演示系统数据库使用 `SQLite`，文件位置：

- `/root/workspace/yolodist/service/backend/data/inference_logs.db`

主要表如下：

- `inference_logs`
  - 推理调用日志
- `inspection_records`
  - 每张图的正式检测记录主表
- `detection_items`
  - 每条记录对应的检测框明细
- `review_notes`
  - 人工复核批注

### 9.6 何时写数据库

当前系统是“检测即落库”：

1. 调用推理接口时：
   - 写入 `inference_logs`
2. 单图检测或文件夹检测成功后：
   - 自动保存到 `inspection_records`
   - 自动保存到 `detection_items`
3. 人工复核保存时：
   - 写入或更新 `review_notes`

### 9.7 记录导出模块当前含义

- `刷新历史`
  - 重新从数据库读取历史记录列表
- `历史记录`
  - 数据库中已保存的图片检测记录
- `导出质检报告(JSON)`
  - 当前仅导出**当前选中记录**，不是整批文件夹导出

### 9.8 还有哪些持久化位置

除了 SQLite 数据库，演示系统还会把上传图片保存到：

- `/root/workspace/yolodist/service/backend/data/uploads/`

如果需要“清空在线演示痕迹”，通常应同时清理：

- `service/backend/data/inference_logs.db`
- `service/backend/data/uploads/`
- 这些额外对比模型更适合写成“经典强基线/补充对照”，不建议替代 `Faster R-CNN MobileNetV3 Large FPN` 作为“略弱于我们方法”的主对比对象。
