# 并行工作步骤文档（训练外可同步推进）

适用场景：当前主线程在服务器训练 `baseline/modified/distill`，其余线程并行推进训练外工作。  
目标：保证多线程协作不冲突、可合并、可复现。

## 1. 当前状态基线

主线程正在进行：

1. `modified_model` 训练
2. `distillation` 训练

当前可用资产：

1. 模型训练/评估框架已可运行
2. PPLA 学生模型已接入
3. `run_manifest.json`、`summary` 工具已可用

## 2. 并行线程总览

建议拆为 5 个并行线程，每个线程使用独立分支，避免写冲突。

1. 线程A：数据增强链路（Prompt + 生成 + 筛选）
2. 线程B：实验结果汇总与论文图表资产
3. 线程C：推理后端服务（Flask API）
4. 线程D：部署导出链路（ONNX/TensorRT准备）
5. 线程E：文档与复现规范（实验记录、模板、检查脚本）

## 3. 统一接口契约（所有线程必须遵守）

### 3.1 模型产物契约

统一输出目录和文件名：

1. `weights/best_teacher.pt`
2. `weights/best_student_plain.pt`
3. `weights/best_student_ppla.pt`
4. `weights/best_student_distill.pt`

说明：

- 训练线程可以先按运行目录输出，收敛后由脚本复制到上述标准名。
- 其它线程（部署/服务/论文）只依赖标准名，不依赖训练目录细节。

### 3.2 结果指标契约

统一汇总到：

1. `reports/metrics_master.csv`

列定义（固定）：

1. `run_id`
2. `model_variant`（baseline/plain/ppla/distill）
3. `dataset_version`
4. `params`
5. `flops`
6. `fps`
7. `map50`
8. `map50_95`
9. `small_recall`
10. `config_path`
11. `weights_path`
12. `commit`
13. `timestamp`

### 3.3 数据增强产物契约

增强数据统一放：

1. `datasets/synthetic/<version>/images/...`
2. `datasets/synthetic/<version>/labels/...`
3. `datasets/synthetic/<version>/manifest.jsonl`

`manifest.jsonl` 每行字段（固定）：

1. `image_path`
2. `label_path`
3. `source`（real/synthetic）
4. `prompt_id`
5. `defect_type`
6. `quality_score`
7. `accepted`（true/false）

### 3.4 后端 API 契约（线程C）

最小可用接口：

1. `GET /api/v1/health`
2. `POST /api/v1/infer`
3. `GET /api/v1/models`
4. `POST /api/v1/models/switch`
5. `GET /api/v1/stats/summary`

`POST /api/v1/infer` 请求（JSON）：

1. `image_path`（string, 必填）
2. `model_name`（string, 可选，默认当前模型）
3. `conf`（float, 可选）

响应（JSON）：

1. `model_name`
2. `latency_ms`
3. `detections`（数组，元素含 `cls/conf/xyxy`）
4. `image_size`

## 4. 各线程详细工作步骤

### 线程A：数据增强链路

代码写入范围：

1. `src/yolodist/data_aug/`
2. `tools/generate_synthetic.py`
3. `tools/filter_synthetic.py`
4. `configs/data_aug/*.toml`

工作步骤：

1. 建立 prompt 模板库（按缺陷类型和严重程度）。
2. 封装生成接口（先预留，可先 mock，不阻塞主线）。
3. 实现质量筛选脚本（阈值 + 人工抽检列表导出）。
4. 生成 `manifest.jsonl`，严格遵守字段契约。

验收标准：

1. 生成版本目录可复现
2. 产物字段完整
3. 可与现有训练数据合并

### 线程B：实验汇总与论文图表

代码写入范围：

1. `src/yolodist/reporting/`
2. `tools/build_report_tables.py`
3. `reports/templates/`

工作步骤：

1. 汇总每次 run 的 `metrics_summary.json` 到 `metrics_master.csv`。
2. 生成论文表格模板（主结果表、消融表、速度表）。
3. 生成图表数据中间文件（csv/json），不绑定具体绘图库。

验收标准：

1. 一条命令可重建 `reports/` 下结果
2. 表头固定，便于论文直接引用

### 线程C：推理后端服务

代码写入范围：

1. `service/backend/`
2. `service/backend/app.py`
3. `service/backend/infer.py`
4. `service/backend/model_registry.py`

工作步骤：

1. 建 Flask 项目骨架与 health 接口。
2. 接入本地模型推理接口（先 PyTorch，后续可切 TensorRT）。
3. 实现模型列表与切换接口。
4. 实现推理日志记录（SQLite）。

验收标准：

1. `curl /api/v1/health` 返回 200
2. `POST /api/v1/infer` 返回结构符合契约
3. 支持切换至少两种模型权重

### 线程D：导出与部署链路

代码写入范围：

1. `tools/export_onnx.py`
2. `tools/build_trt_engine.sh`
3. `deploy/`

工作步骤：

1. 固化 ONNX 导出命令和参数。
2. 固化 TensorRT 构建脚本（FP16 优先）。
3. 输出部署测试记录模板。

验收标准：

1. 能导出 `.onnx`
2. 有标准化命令和日志模板
3. 与后端推理接口可对接

### 线程E：文档与复现规范

代码写入范围：

1. `docs/`
2. `tools/validate_run_artifacts.py`

工作步骤：

1. 维护线程同步文档和里程碑记录。
2. 写“实验复现最短路径”文档。
3. 写结果产物检查脚本（检查必须文件是否齐全）。

验收标准：

1. 新成员能在 30 分钟内理解并复现实验链
2. 任何 run 都能被脚本校验完整性

## 5. Git 协作规范

分支命名：

1. `codex/thread-a-data-aug`
2. `codex/thread-b-reporting`
3. `codex/thread-c-backend`
4. `codex/thread-d-deploy`
5. `codex/thread-e-docs`

提交要求：

1. 每次提交说明“改了什么 + 为什么”
2. 不提交大体积数据和模型权重
3. 每线程只改自己负责目录（减少冲突）

合并门槛：

1. 语法检查通过
2. 文档同步更新（至少在 `WORKLOG` 追加一步）
3. 关键接口契约不破坏

## 6. 每日同步机制（建议）

每天固定一次更新：

1. 更新 `docs/WORKLOG.md`
2. 在 `reports/` 更新当日产物摘要
3. 标记阻塞项（需要主线程决策的单独列出）

建议固定字段：

1. `today_done`
2. `today_metrics`
3. `blockers`
4. `next_actions`

## 7. 你现在可以直接下发给其他线程的任务

1. 线程A先完成 `manifest` 契约和筛选脚本。
2. 线程B先完成 `metrics_master.csv` 自动聚合。
3. 线程C先完成后端 `health + infer` 两个接口。
4. 线程D先完成 ONNX 导出工具。
5. 线程E先完成 run 产物校验脚本。

这样主线程训练结束后，其他模块可以无缝接入，不需要等待。
